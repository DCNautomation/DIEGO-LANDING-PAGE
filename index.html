Trusvana: a real estate CRM I built

A working CRM for real estate teams, designed and coded from scratch. Screenshots below use placeholder data.

People inquire about buying, renting or selling through a public form, and agents work each lead through a pipeline from New to Closed. It handles lead routing (first to claim or round robin), follow-up dates, tasks assigned to teammates, a closing checklist for every deal, saved filters, a timeline on each lead, reports and a calendar. It also exposes a read-only API that n8n workflows use for speed-to-lead alerts and a daily digest.

Leads pipeline

Problems it solves

Customer information gathering

Instead of typing customer details into an Excel sheet by hand, people fill in a public inquiry form: name, contact details, buy, rent or sell, budget, area and the property they like. It goes straight into the CRM as a new lead and is routed to an agent, with a spam check built in.

Duplicate leads

When a new lead has the same email or phone as an existing one, both are tagged "check duplicate" and a note is added to their timelines, so a person can review them instead of two agents chasing the same client. Nothing is deleted automatically.

Exporting leads

An Export CSV button downloads leads for a date range, a pipeline stage, a teammate or follow-ups due. The file opens cleanly in Excel, and cells that could run as spreadsheet formulas are neutralized.

What it's built with

Front end

React and TypeScript, built with Vite. Styled with Tailwind CSS and shadcn/ui components, routed with React Router, set in the Geist typeface.

Back end

Python and Flask serving a JSON API. Password logins with hashed passwords, CSRF protection, login lockout, a spam check on the public form and strict security headers.

Database

SQLite, queried with plain parameterized SQL and no ORM. Tables cover leads, properties, tasks, transactions, tags, saved views and a timeline of every change.

Hosting and deploys

Runs on PythonAnywhere. A push to GitHub starts a GitHub Actions build and smoke test, then uploads the app and reloads the site automatically.

Automation

Token-protected read-only endpoints feed importable n8n workflows: a speed-to-lead alert for new inquiries and a daily digest of follow-ups due.

Automation Hub: automations that fail loudly

A run board for webhook automations. Runs on my machine for now, and the screenshots show seeded demo data.

Most automations only get tested for the day everything works. This one is built for the day it doesn't. Apps and n8n flows send it signed webhooks, it queues each one, retries the ones that fail, and gives up cleanly with a plain-language reason when retries run out. Every run keeps its payload, every try and a history of who did what, so a failure never disappears.

Walkthrough video, about 7 minutes.

Runs board

Problems it solves

Silent failures

A failed run lands in a Needs attention view with the exact error, so a lost order or missed lead gets noticed the same day. Alerts for runs that give up are built and tested, and not connected to a live Telegram bot yet.

Duplicates and bad requests

An idempotency key means the same event never runs twice. Requests are signed with a shared secret and expire after 5 minutes, so an old request can't be replayed.

Temporary problems

Retries back off with a bit of randomness, up to a limit set per source. After the last try the run is marked Gave up, and an admin can retry it with one click.

What it's built with

Back end

Python and FastAPI take in the webhooks. A separate worker process runs the jobs, so slow work never blocks incoming requests.

Database and queue

PostgreSQL 16 stores everything and is also the job queue. Workers claim jobs with FOR UPDATE SKIP LOCKED, so two workers never take the same job. No Redis needed.

Dashboard

React and TypeScript, served by nginx in Docker. Login with admin and viewer roles, lockout after repeated failed logins, and times shown in Philippine time.

Safety and testing

The app connects to the database with a limited role that can't alter or rewrite the audit log, and the log blocks edits and deletes at the database level. The dashboard has a strict content security policy. 374 automated API tests run against a real Postgres at 97% coverage, plus tests for the dashboard.

Veliora Stock: inventory for a spirits distributor

Inventory and order management built for a whiskey and spirits distributor. The brands and retail prices are real, and the costs, B2B prices and customers are made up.

Stock is never typed in by hand. Every bottle in or out is a row in a ledger that can't be edited, and the database itself refuses to sell a bottle that isn't there. Orders move from draft to confirmed to fulfilled, profit is worked out per order, and any order prints as an invoice.

Open the live demo Free hosting, so the first load can take about 20 seconds.

Walkthrough video, about 8 minutes.

Dashboard

Problems it solves

Counts that drift

Stock on hand is calculated from the ledger by the database, not typed in. A mistake is fixed with a new entry, so there is always a trail of what changed and why.

Overselling

Negative stock is impossible, even from a raw SQL insert. When two orders race for the last bottle, exactly one wins. This is tested with real concurrent requests.

Not knowing the margin

Profit per order uses the average cost at the moment the bottles shipped. Retail and B2B customers get their own prices, and reports cover each month and each product.

What it's built with

Front end

React and TypeScript with Vite and Tailwind. A root error boundary keeps one bad response from blanking the whole app.

Back end

Python and Flask serving a JSON API. Admin and staff roles, a read-only demo login, CSRF protection and lockout after 5 bad passwords.

Database

PostgreSQL 16 with plain SQL and no ORM. Triggers keep stock and average cost correct, and a second trigger blocks edits to the ledger. 69 tests run against a real Postgres.

Automation and exports

A token-protected low-stock feed plugs into n8n for reorder messages. Products, orders, stock movements and sales reports export to CSV, with cells neutralized so a spreadsheet never runs one as a formula.
